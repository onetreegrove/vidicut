## 文档结构

### 1. 适用范围与实测证据

记录本次实测对象和结果：

- 主页 URL 与 `sec_user_id` 的提取规则。
- 博主页面显示 173 个作品。
- `/aweme/v1/web/aweme/post/` 共返回 10 页，按 `aweme_id` 去重后 173 条。
- 其中 171 条普通视频、2 条图文。
- 实测页大小与 cursor 链只作为样本证据，不写成固定规则。

### 2. 主页作品接口

记录接口：

```text
GET https://www.douyin.com/aweme/v1/web/aweme/post/
```

按类别解释参数，而不是只堆一条不可维护的完整 URL：

- 业务参数：`sec_user_id`、`max_cursor`、`count`、`from_user_page`、`locate_query`、`need_time_list`、`time_list_query`、`publish_video_strategy_type`、`show_live_replay_strategy`。
- Web 客户端参数：`aid`、`device_platform`、`channel`、`pc_client_type`、版本、浏览器、系统、屏幕和网络信息。
- 会话参数：`webid`、`uifid`、`verifyFp/fp`、`msToken`。
- 动态校验参数：`a_bogus`、`x-secsdk-web-signature`、`timestamp`。

每个参数注明：本次观察值、是否随分页变化、是否应由调用者配置、是否禁止写死。

### 3. 请求头与 Cookie

列出最低请求形态：

- `User-Agent`
- `Referer: https://www.douyin.com/`
- `Accept`
- `Accept-Language`
- 当前网页会话 Cookie

明确：Cookie、签名、token 属于敏感且短期的数据，示例只使用占位符；文档不保存本次真实值。

### 4. 首次请求与分页流程

给出完整状态机：

1. 从 `/user/<sec_user_id>` 解析用户标识。
2. 第一页使用 `max_cursor=0`。
3. 校验 HTTP 状态和 JSON `status_code`。
4. 消费 `aweme_list`，按 `aweme_id` 去重。
5. 从响应读取 `max_cursor`，不能自行按时间或数量递增。
6. `has_more=1` 时带新 cursor 请求下一页。
7. `has_more=0` 时结束。
8. 检测重复 cursor、空页但仍有更多、连续无新增作品，防止死循环。
9. 达到用户数量上限时提前停止。

同时记录响应关键字段：`status_code`、`min_cursor`、`max_cursor`、`has_more`、`aweme_list`、`time_list`、`request_item_cursor`、`post_serial`。

### 5. 作品类型判断

说明不能只看是否存在 `video`：

- 普通视频：本次主要表现为 `aweme_type=0`、`media_type=4`。
- 图文：本次表现为 `aweme_type=68`、`media_type=2`，并带非空 `images`。
- 图文响应也可能带 `video`，其用途可能是图文播放/配乐，不应当成主页普通视频下载。
- 后续“只下载视频”的实现以作品类型与 `images` 联合判断，图文计数后跳过。

### 6. 视频地址和清晰度选择

记录字段优先级：

1. 在 `video.bit_rate[]` 中筛选 `format=mp4`、`is_h265=0`、`play_addr.url_list` 非空的候选。
2. 按 `bit_rate` 降序选择最高码率 H.264 MP4。
3. 回退 `video.play_addr_h264.url_list`。
4. 再回退 `video.play_addr.url_list`。
5. `url_list` 依次作为 CDN 后备地址。

说明本次 171 条视频都有 `play_addr` 和 `bit_rate[]`，但都没有 `download_addr`，因此不能依赖所谓固定下载字段。记录样本 Range 请求返回 `206` 和 `video/mp4`，但要求实际下载时仍校验响应。

### 7. CDN 下载流程

说明：

- 携带抖音 `Referer` 和匹配会话的 User-Agent。
- 跟随重定向。
- 使用流式写入和 `.part` 临时文件。
- 校验 200/206、媒体类型、非零文件长度。
- 当前地址失败时尝试同一 `url_list` 的后备 CDN。
- 401/403/404 或所有 CDN 失败时，重新获取作品页数据刷新地址。
- CDN URL 可能过期，不应作为永久下载地址或长期写入公开清单。

### 8. 直接调用方式示例

提供三种脱敏示例：

- 一条带占位符的 `curl` 首次请求。
- 一条下一页 cursor 请求。
- Bun `fetchProfilePage()` 伪代码，展示 URLSearchParams、响应校验和返回 cursor，不包含签名生成算法。

明确示例中的 `<A_BOGUS>`、`<MS_TOKEN>`、`<COOKIE>` 等必须来自有效会话，不能照抄。

### 9. 直接接口方案的已知限制

单独列出证据等级：

- 已验证：真实 Chrome 页面能够成功请求该接口；响应结构、分页 cursor、作品类型和媒体字段已经实测。
- 未验证：仅使用当前 downloader 的 `ttwid + Referer + User-Agent` 是否能稳定直接调用主页接口。
- 未验证：分页时复用首请求的 `a_bogus` 或签名是否有效。
- 高风险假设：自行生成或长期固化 `a_bogus/msToken/verifyFp`。
- 可能响应：403/429、HTTP 200 但 `status_code != 0`、空 `aweme_list`、验证码或风控页。

文档不会宣称接口是官方公开 API，也不会把动态签名逆向实现作为既定方案。

### 10. 后续实现决策点

文档结尾保留三个待选实现路径：

- 用户提供 Cookie，CLI 直接请求，签名缺失时明确失败。
- 用户提供从 DevTools 导出的完整首请求模板，CLI解析并尝试更新 cursor；必须标注短期有效和分页签名风险。
- 使用 Chrome/CDP 让网页生成合法请求，再由 downloader消费响应。

这一步只形成事实文档；文档完成并审阅后，再根据实际直连接口试验结果确定 `profile` 命令采用哪条路径。
